1 · Setup: Background SHAP at a Leaf

In background (interventional) SHAP, the model's prediction is explained by comparing a consumer data point $\mathbf{x}$ against a background dataset $\mathcal{B} = \{b_1, \ldots, b_m\}$. The background Shapley value of feature $k$ for consumer $\mathbf{x}$ can be viewed as the average of baseline SHAP over all baselines $b \in \mathcal{B}$, where each baseline SHAP explains the difference $f(\mathbf{x}) - f(b)$ using the Shapley-weighted coalition average.

WOODELF decomposes this computation tree-by-tree, leaf-by-leaf. At each leaf $\ell$ with leaf weight $w_\ell$, we need the S-vector: a per-feature array of shape $(U_c,)$ giving each unique consumer pattern's contribution to the final Shapley values from this leaf.

Key quantities at one leaf
SymbolMeaning
$D$Number of unique features along the root-to-leaf path
$w_\ell$Leaf prediction value (weight)
$U_c$Number of unique consumer decision patterns at this leaf
$U_b$Number of unique background decision patterns at this leaf
$\hat{b}_j$Frequency of background pattern $j$ (fraction of background rows)

The MN approach processes each of the $U_c$ unique consumer patterns against each of the $U_b$ unique background patterns — hence the name "MN" (after the two dataset sizes). Crucially, $U_c \ll n$ and $U_b \ll m$ because many rows land in the same leaf and receive identical binary patterns.

2 · Decision Patterns and the WDNF

Each data point is routed through the tree by comparing feature values to thresholds at each internal node. Encoding the result as bits gives a compact integer representation.

Decision pattern encoding

For the $D$ features on the path (in order), bit $d$ of the integer pattern is 1 if the data point follows the path at that node (i.e. goes in the same direction the path does — left or right), and 0 if it diverges from the path.

WDNF cube from a (consumer, background) pair

WOODELF represents the leaf's characteristic function as a Weighted Disjunctive Normal Form (WDNF). For a given consumer pattern $c$ and background pattern $b$, the relevant cube has:

Bit configuration Meaning for feature $d$ Role in cube
$c_d = 1,\ b_d = 0$ Consumer follows the path, background diverges Positive literal — feature $d \in s^+$
$c_d = 0,\ b_d = 1$ Consumer diverges from the path, background follows Negative literal — feature $d \in s^-$
$c_d = 1,\ b_d = 1$ Both follow the path Null player — feature $d \notin s$, no contribution
$c_d = 0,\ b_d = 0$ Both diverge from the path Invalid pair — we will never traverse in this direction, no cube will be created (filtered out)

The validity condition filters out all pairs $(c, b)$ where for some feature $d$ both $c_d = 0$ and $b_d = 0$ — i.e. both consumer and background diverge from the path at $d$. When this happens, no interpolated coalition (formed by choosing feature values from either $c$ or $b$) can ever traverse the path in the $d$-direction, so the leaf is unreachable from that direction and no WDNF cube is created for this pair.

Bit-level, $c_d = 0$ and $b_d = 0$ simultaneously iff bit $d$ of $(c \mathbin{|} b)$ is $0$. So the condition "no feature has both sides diverging" is equivalent to all bits of $(c \mathbin{|} b)$ being $1$:

$$\text{valid}(c, b) = \bigl[(c \mathbin{|} b) = \underbrace{11\cdots1}_{D}\bigr]$$

In code: (consumer | background) == (1 << D) - 1. Pairs that fail are masked to zero before any contribution is computed.

3 · Symmetry: Contributions Depend Only on Counts

Symmetry insight

Let $p = |s^+|$ and $n = |s^-|$ for a given (consumer, background) pair. By symmetry, every positive literal contributes the same amount to its own Shapley value, and every negative literal contributes the same amount. Call these:

$$\alpha(p, n) = \text{contribution of each feature in } s^+$$ $$\beta(p, n) = \text{contribution of each feature in } s^-$$

For Shapley values specifically (from the WDNF formula in the paper): $$\alpha(p,n) = \frac{1}{p \cdot \binom{p+n}{p}}, \qquad \beta(p,n) = \frac{-1}{n \cdot \binom{p+n}{n}}$$

4 · Precomputed Contribution Tables

At initialization, the algorithm precomputes two $(D{+}1) \times (D{+}1)$ lookup tables covering all valid $(p, n)$ combinations: 

for p in range(D + 1):
    for n in range(D + 1 - p):
        s_plus  = set(range(p))           # use feature indices 0..p-1 as proxies
        s_minus = set(range(p, p + n))    # use indices p..p+n-1 as proxies
        contributions = metric.calc_metric(s_plus, s_minus)
        pos_matrix[p][n] = contributions.get(0, 0.0)   # feature 0 ∈ s_plus
        neg_matrix[p][n] = contributions.get(p, 0.0)   # feature p ∈ s_minus
Why integer proxies work

The metric is symmetric, so the actual feature names don't matter for the contribution value — only the counts $p$ and $n$. Using integer proxies $\{0,\ldots,p{-}1\}$ for $s^+$ and $\{p,\ldots,p{+}n{-}1\}$ for $s^-$ gives the same contribution values as using the real feature names, at a fraction of the setup cost.

The two tables are computed once per MNBackgroundPathToSVectors instance and reused across all leaves and all trees. The cost is $O(D^2)$ metric evaluations at construction time.

5 · Base Algorithm — MNBackgroundPathToSVectors

The base class implements the core vectorized computation in _compute_s_batch. It processes a batch of unique consumer patterns against all unique background patterns simultaneously.

Step-by-step walkthrough

1
Uniquify background patterns. pd.Series.value_counts(normalize=True) compresses $m$ background rows into $U_b$ unique patterns with their frequencies $\hat{b}_j$. This is the key complexity reduction: subsequent work scales with $U_b$, not $m$.
2
Compute diff, positive, negative (shape: U_c × U_b).
$$\text{diff}_{c,b} = c \oplus b \qquad \text{(bits that differ)}$$ $$\text{positive}_{c,b} = c \mathbin{\&} \text{diff}_{c,b} \qquad \text{(bits where } c_d=1, b_d=0\text{)}$$ $$\text{negative}_{c,b} = b \mathbin{\&} \text{diff}_{c,b} \qquad \text{(bits where } c_d=0, b_d=1\text{)}$$
3
Count bits and look up per-pair contributions. For each (consumer, background) pair we count how many features are positive literals and how many are negative, then look up the per-literal contribution from the precomputed tables: $$p_{c,b} = \text{popcount}(\text{positive}_{c,b}), \quad n_{c,b} = \text{popcount}(\text{negative}_{c,b})$$ The contribution of every positive literal in the cube is $\alpha(p_{c,b}, n_{c,b})$, and of every negative literal is $\beta(p_{c,b}, n_{c,b})$. Multiplying by the background frequency $\hat{b}_b$ and the validity mask gives the final weighted contribution for this pair: $$\text{pos_weighted}_{c,b} = \alpha(p_{c,b},\, n_{c,b}) \cdot \hat{b}_b \cdot \text{valid}_{c,b}$$ $$\text{neg_weighted}_{c,b} = \beta(p_{c,b},\, n_{c,b}) \cdot \hat{b}_b \cdot \text{valid}_{c,b}$$ The result is two $(U_c \times U_b)$ arrays holding the scalar contribution of each literal type for every pair.
4
Route contributions to the right feature positions and sum over backgrounds. So far we have a scalar weight for every (consumer, background) pair, but we need to assign it to the specific features that are positive or negative literals in that pair's cube. bits_matrix unpacks the positive and negative integers into binary $(D \times U_c \times U_b)$ tensors, giving a 1 at position $[d, c, b]$ exactly when feature $d$ is a positive (or negative) literal for that pair. Multiplying elementwise by pos_weighted or neg_weighted — both broadcast from $(U_c \times U_b)$ to $(D \times U_c \times U_b)$ — and contracting along the $U_b$ axis gives the final S-vector for each consumer pattern: $$\mathbf{s} = \bigl(\mathbf{pos_bits} \odot \mathbf{pos_weighted} + \mathbf{neg_bits} \odot \mathbf{neg_weighted}\bigr)_{(D \times U_c \times U_b) \to (D \times U_c)} \cdot w_\ell$$ The output $\mathbf{s}$ has shape $(D \times U_c)$: one value per feature per unique consumer pattern, ready to be scattered back to the full consumer dataset via the factorize inverse index.

5.5 · Batching to Avoid Memory Explosion

The 3D tensors pos_bits and neg_bits in the base class have shape $(D \times U_c \times U_b)$. For large $U_c$ or $U_b$ this can exhaust RAM. For example, $D = 18$, $U_c = 1000$, $U_b = 1000$ already requires $18 \times 1000 \times 1000 = 18\text{M}$ entries per tensor.

Batching strategy

The background patterns $U_b$ are fixed for the whole leaf, so the safe chunk size for the consumer dimension is: $$\text{chunk} = \left\lfloor \frac{\text{BATCH_SIZE}}{U_b} \right\rfloor$$ If $U_c \leq \text{chunk}$, the entire computation runs in one call (the common case). Otherwise $U_c$ is split into chunks of size chunk and the results are concatenated along the $U_c$ axis. Either way, the peak 3D allocation is bounded by $D \times \text{BATCH_SIZE}$ entries, regardless of $U_c$.

The faster class (MNBackgroundFasterPathToSVectors) never allocates the 3D tensor at all, so it can afford a 10× larger BATCH_SIZE and still uses far less peak memory than the base class at its smaller limit.

6 · Faster Algorithm — MNBackgroundFasterPathToSVectors

MNBackgroundFasterPathToSVectors overrides only _compute_s_batch. Everything else — construction, uniquification, batching, neighbor trick — is inherited unchanged. The key improvement is eliminating the 3D tensor by factorizing bit spreading into two matrix multiplications.

The factorization identity

Bit $d$ of the positive integer is set iff the consumer follows the path at $d$ AND the background diverges:

$$\text{pos_bits}[d, c, b] = c_d \cdot (1 - b_d)$$

Bit $d$ of the negative integer is set iff the consumer diverges from the path at $d$ AND the background follows:

$$\text{neg_bits}[d, c, b] = (1 - c_d) \cdot b_d$$

where $c_d$ and $b_d$ are the $d$-th bits of consumer and background patterns respectively.

Substituting into the sum over backgrounds and pulling $c_d$ outside (it doesn't depend on $b$):

$$s[d, c] = c_d \cdot \underbrace{\sum_b (1 - b_d) \cdot \text{pos_weighted}_{c,b}}_{\text{total_pos}[c] - \text{BPW}[d,c]} + (1 - c_d) \cdot \underbrace{\sum_b b_d \cdot \text{neg_weighted}_{c,b}}_{\text{BNW}[d,c]}$$

Define the two matrix products:

$$\mathbf{BPW} = \mathbf{b_bits} \cdot \mathbf{pos_weighted}^\top \qquad (D \times U_c)$$ $$\mathbf{BNW} = \mathbf{b_bits} \cdot \mathbf{neg_weighted}^\top \qquad (D \times U_c)$$

where $\mathbf{b_bits}$ is the $(D \times U_b)$ binary matrix of background patterns. Let $\text{total_pos}[c] = \sum_b \text{pos_weighted}_{c,b}$. Then the formula collapses to:

$$\boxed{s = \mathbf{BNW} + \mathbf{c_bits} \odot \bigl(\text{total_pos} - \mathbf{BPW} - \mathbf{BNW}\bigr)}$$

The two dominant operations are now BLAS-optimized matrix multiplications on 2D matrices — no 3D tensor is ever allocated.

Operations in code

c_bits = bits_matrix(consumer_batch, D)      # (D, U_c)
b_bits = bits_matrix(unique_b, D)             # (D, U_b)

BPW = b_bits @ pos_weighted.T               # (D, U_b) @ (U_b, U_c) → (D, U_c)
BNW = b_bits @ neg_weighted.T               # (D, U_b) @ (U_b, U_c) → (D, U_c)
total_pos = pos_weighted.sum(axis=1)       # (U_c,)

return (BNW + c_bits * (total_pos - BPW - BNW)) * w
Base class

Peak allocation: two $(D \times U_c \times U_b)$ boolean tensors

Dominant op: elementwise multiply + reduce along axis 2

BATCH_SIZE: 1,000,000

Cache behavior: poor — 3D strides jump around in memory

Faster class

7 · Full Derivation of the Factorization

Starting from the definition of $s[d, c]$ in the base class:

$$s[d, c] = \sum_b \bigl(\text{pos_bits}[d,c,b] \cdot \text{pos_weighted}_{c,b} + \text{neg_bits}[d,c,b] \cdot \text{neg_weighted}_{c,b}\bigr)$$
↓ substitute factorization identities
$$= \sum_b \bigl[c_d(1-b_d)\cdot \text{pos_weighted}_{c,b} + (1-c_d)b_d\cdot \text{neg_weighted}_{c,b}\bigr]$$
↓ pull $c_d$ and $(1-c_d)$ outside the sum (independent of $b$)
$$= c_d \sum_b(1-b_d)\cdot\text{pos_weighted}_{c,b} + (1-c_d)\sum_b b_d\cdot\text{neg_weighted}_{c,b}$$
↓ split first sum into total minus $b_d$-weighted part
$$= c_d\Bigl[\underbrace{\sum_b\text{pos_weighted}_{c,b}}_{\text{total_pos}[c]} - \underbrace{\sum_b b_d\cdot\text{pos_weighted}_{c,b}}_{\text{BPW}[d,c]}\Bigr] + (1-c_d)\underbrace{\sum_b b_d\cdot\text{neg_weighted}_{c,b}}_{\text{BNW}[d,c]}$$
↓ expand and collect $\text{BNW}$
$$s[d,c] = \text{BNW}[d,c] + c_d\bigl(\text{total_pos}[c] - \text{BPW}[d,c] - \text{BNW}[d,c]\bigr)$$

The two sums $\text{BPW}$ and $\text{BNW}$ are computed in one matrix multiplication each: $\mathbf{b\_bits} \in \mathbb{R}^{D \times U_b}$ times $\mathbf{pos\_weighted}^\top \in \mathbb{R}^{U_b \times U_c}$.

8 · Neighbor Leaf Trick

Some leaves can be merged with their sibling to save computation. When a left leaf $\ell$ has a right sibling $\ell'$ that is also a leaf and whose feature does not repeat elsewhere in the path, the two leaves can be processed together.

Why flipping the LSB works

Because neighbor leaves share all inner nodes and agree on the split traversal in all of them except the very last split, flipping the least-significant bit of a pattern (which encodes that last split) converts any pattern that lands in $\ell$ into the corresponding pattern that would have landed in $\ell'$.

The neighbor's contribution uses weight $w' = w_{\ell'}$ and the flipped patterns:

$$\text{result}(c) = \underbrace{\text{s-matrix}(c,\; \mathcal{B},\; w_\ell)}_{\text{own leaf}} + \underbrace{\text{s-matrix}(c \oplus 1,\; \mathcal{B} \oplus 1,\; w')}_{\text{sibling leaf via recursion}}$$

In code this is a single recursive call at the end of get_background_s_matrix, with both consumer and background patterns XORed with 1 (flip LSB) and $w$ replaced by $w'$. The recursion depth is always 1 — the flipped call never has a non-None w_neighbor.

9 · Complexity Summary

Let $T$ = trees, $L$ = leaves per tree, $D$ = depth of a leaf path, $n$ = consumer rows, $m$ = background rows, $U_c$ = unique consumer patterns per leaf, $U_b$ = unique background patterns per leaf.

SHAP package / naive O(mn)
$O(\mathbf{m \cdot n \cdot T \cdot L \cdot D})$
MNBackgroundPathToSVectors
$O(mTL + nTLD + \mathbf{U_c \cdot U_b \cdot T \cdot L \cdot D})$
MNBackgroundFasterPathToSVectors
$O(mTL + nTLD + \mathbf{U_c \cdot U_b \cdot T \cdot L \cdot D})$
Why $U_c \ll n$ and $U_b \ll m$

For each leaf, every consumer (and background) data point is assigned a $D$-bit decision pattern encoding whether it follows or diverges from the path at each of the $D$ nodes. Because there are only $D$ bits, at most $2^D$ distinct patterns can exist, so $U_c \leq \min(n,\, 2^D)$ and $U_b \leq \min(m,\, 2^D)$. For deep paths $2^D$ is the binding constraint, and in practice patterns concentrate around a small number of common follow/diverge combinations.

When does MN win over HighDepth (WOODELF's anti-diagonal approach)?

The HighDepth backend costs $O(2^D \cdot D^2)$ per leaf (all $2^D$ consumer pattern slots pre-filled). MN costs $O(U_c \cdot U_b \cdot D)$. MN is faster when:

$$U_c \cdot U_b < 2^D \cdot D \quad\Longleftrightarrow\quad \text{small datasets relative to tree depth}$$

This is why hybrid_woodelf switches to MN when $D > 12$ (where $2^D$ becomes prohibitively large for the HighDepth backend).

10 · Any-Order Interaction Values — Intuition

So far each feature received its own value. An interaction value of order $k$ asks a different question: how much does the joint presence of a set $S = \{d_1, \ldots, d_k\}$ of features explain, beyond what its individual members and its smaller sub-coalitions already explain? Formally it is the Grabisch–Roubens index, built on the discrete derivative — the alternating sum that isolates exactly the joint effect:

$$I(S) = \sum_{T \subseteq M \setminus S} w(|T|)\, \underbrace{\sum_{L \subseteq S} (-1)^{k - |L|}\, v(T \cup L)}_{\Delta_S v(T)}$$

For $k = 1$ the derivative is $v(T \cup \{d\}) - v(T)$ and $I$ is the ordinary Shapley (or Banzhaf) value — so everything below is a strict generalization of sections 1–9. For $k = 2$ it is the familiar $v(T{+}i{+}j) - v(T{+}i) - v(T{+}j) + v(T)$.

Why this stays easy on a cube

WOODELF never applies this to the whole model — only to a single cube at a time, and a cube is an extremely rigid game. Its characteristic function is $v(T) = \bigl[s^+ \subseteq T\bigr]\bigl[s^- \cap T = \emptyset\bigr]$: it fires only when every positive literal is present and no negative literal is. Two consequences make the whole extension tractable:

The two facts that drive everything

1 · Features outside the cube are dummies. A feature that appears in neither $s^+$ nor $s^-$ cannot change $v$ at all, and the interaction index of any set containing a dummy is $0$. So a subset $S$ contributes only when all $k$ of its features are literals of the cube — this single containment test is what the algorithms spend their effort on.

2 · Only counts matter. Given containment, the derivative $\Delta_S v(T)$ is non-zero for exactly one coalition $T$, and the index collapses to a closed form that depends on nothing but four integers: how many positive and negative literals the cube has, and how many of $S$'s features sit on each side.

This is the exact generalization of the symmetry insight of section 3, where $\alpha(p,n)$ and $\beta(p,n)$ depended only on the counts $(p, n)$. Section 3 is the $k = 1$ case of what follows.

The four numbers

A cube and a subset are therefore encoded by the tuple $(n,\, p,\, a,\, k - a)$: the cube's negative and positive literal counts, and the split of $S$ across them.

Worked example

Cube $x_1 \wedge x_4 \wedge \neg x_2 \wedge \neg x_5$ with subset $S = \{x_1, x_2, x_5\}$ (so $k = 3$):

QuantityValueWhy
$n$ — cube negative literals2$\neg x_2, \neg x_5$
$p$ — cube positive literals2$x_1, x_4$
$a$ — subset ∩ positives1$x_1$
$k - a$ — subset ∩ negatives2$x_2, x_5$

Encoded as $(2, 2, 1, 2)$. Every subset of every cube that shares these four numbers has the identical value — which is precisely why a small lookup table can replace all metric evaluations.

The closed forms

Carrying out the collapse gives one line per metric. With $k$ the order, $a = |S \cap s^+|$ and $k - a = |S \cap s^-|$:

$$I_{\text{Shapley}}(S) = (-1)^{\,k-a}\ \frac{(p-a)!\ \bigl(n-(k-a)\bigr)!}{(p+n-k+1)!} \qquad\qquad I_{\text{Banzhaf}}(S) = \frac{(-1)^{\,k-a}}{2^{\,p+n-k}}$$

The sign $(-1)^{k-a}$ is the whole intuition in one factor: each of $S$'s features that must be absent for the cube to fire flips the direction of the joint effect. Setting $k = 1$ recovers section 3 exactly — $a = 1$ gives $\frac{(p-1)!\,n!}{(p+n)!} = \alpha(p,n)$ and $a = 0$ gives $-\frac{p!\,(n-1)!}{(p+n)!} = \beta(p,n)$. Setting $k = 2$ reproduces the pairwise interaction formulas of the paper.

The generic interface

Nothing above is specific to Shapley or Banzhaf, so the code takes the four numbers as the contract. A metric subclasses CardinalityInteractionIndicesMetric and implements a single method: 

def cardinality_value(self, num_neg_literals, num_pos_literals, num_subset_pos, num_subset_neg) -> float:
    # the value of one subset of one cube, given only the four counts

GeneralShapleyInteractionValues and GeneralBanzhafInteractionValues are the two built-in implementations, but any cardinality-expressible index (Shapley–Taylor and friends) plugs in the same way and immediately gets both algorithms below.

One metric, a range of orders

An order is not baked into the metric class. A metric carries an interval min_order…max_order and reports every subset whose size falls inside it — so a single pass can produce orders 1, 2 and 3 together rather than requiring three runs. The upper end is capped by the number of variables actually in the cube, since any larger subset must contain a dummy player and is therefore $0$ anyway:

$$\texttt{orders}(V) = \bigl[\,\texttt{min_order},\ \min(\texttt{max_order},\, V)\,\bigr]$$
The useful configurations
ConstructorReports
GeneralShapleyInteractionValues()The default: every order at once — the full interaction hierarchy
GeneralShapleyInteractionValues(3, 3)Order 3 only
GeneralShapleyInteractionValues(1, 2)Ordinary values plus pairwise interactions

Because max_order=None means "no upper limit", the default constructor is the any-order metric. Both algorithms below consume metric.orders(D) directly, so widening the range costs one extra block of rows rather than another pass over the data.

Key convention

Every subset is keyed once, by its sorted tuple of feature names, holding the full value. The shap package instead splits a pair's value across both of its orderings $(f_1, f_2)$ and $(f_2, f_1)$; passing shap_convention=True to GeneralShapleyInteractionValues divides by the subset's size factorial to reproduce that. Mirroring the keys is a separate, downstream concern (CubeMetric.should_mirror), which matters because at order $k$ full mirroring would mean $k!$ copies of every value.

11 · The Simple Approach — MNBackgroundCIIPathToSVectors

The simple class keeps the entire pipeline of section 5 — uniquify the background, build diff / positive / valid, popcount to get $(p, n)$ — and changes only what happens afterwards. Two things generalize.

Generalization 1: the tables gain a dimension

Section 4 precomputed two $(D{+}1) \times (D{+}1)$ tables, one for positive literals and one for negative. At order $k$ a subset is no longer "positive" or "negative" — it is split $a$ against $k - a$ — so the two tables become $k{+}1$ tables indexed by that split:

$$V_a[p][n] \;=\; \texttt{cardinality_value}(n,\, p,\, a,\, k-a), \qquad a = 0, \ldots, k$$

Entries that cannot occur ($a > p$, $k - a > n$, or $p + n < k$) stay $0$, which conveniently makes unreachable splits contribute nothing without a branch. For $k = 1$ this is literally the old pair: $V_1$ is pos_matrix and $V_0$ is neg_matrix. Cost is $O(k \cdot D^2)$ metric calls, once per instance.

Generalization 2: loop over the subsets

Instead of routing a scalar to individual bits, we now ask the containment question of section 10 for each of the $\binom{D}{k}$ subsets of path features. Both parts of that question are single bit-operations. Writing $\text{mask}_S$ for the integer with $S$'s bits set:

The two bit tests

Containment — every feature of $S$ is a literal of this pair's cube exactly when every bit of $S$ differs between consumer and background, since a bit lies in $s^+ \cup s^-$ precisely when it is set in diff:

$$\text{covered}_{S,c,b} = \bigl[(\text{diff}_{c,b} \mathbin{\&} \text{mask}_S) = \text{mask}_S\bigr]$$

The split — of those, the ones that are positive literals are the bits also set in positive, so the count $a$ is one popcount:

$$a_{S,c,b} = \text{popcount}(\text{positive}_{c,b} \mathbin{\&} \text{mask}_S)$$

With $(a, p, n)$ in hand the value is a table lookup, and summing over the background axis finishes the row for subset $S$:

$$s[S, c] \;=\; w_\ell \sum_b V_{a_{S,c,b}}\bigl[p_{c,b}\bigr]\bigl[n_{c,b}\bigr] \cdot \hat{b}_b \cdot \text{valid}_{c,b} \cdot \text{covered}_{S,c,b}$$ 
for s_index, subset in enumerate(subsets):        # all C(D, k) subsets of the path features
    subset_mask = 0
    for d in subset:
        subset_mask |= 1 << (D - 1 - d)

    covered = (diff & subset_mask) == subset_mask     # S sits entirely inside the cube
    a       = np.bitwise_count(positive & subset_mask)  # how many of S are positive literals
    s[s_index] = (contribution_tables[a, p, n] * base * covered).sum(axis=1)

The loop above covers one order. Since a metric may report a range of them, the s-matrix stacks the orders into blocks: rows $\binom{D}{k}$ for each reported $k$, laid out in order and addressed by _order_row_blocks, for a total of $\sum_{k \in \texttt{orders}(D)} \binom{D}{k}$ rows against $U_c$ columns — one row per subset instead of one per feature. Each row is keyed by its sorted feature tuple.

Everything downstream is unchanged: the batching of section 5.5, the scatter through the factorize inverse, and the neighbor trick of section 8 all operate on keys and never inspect them.

Why this is the class in use

Exactly as in section 5, this is the readable reference implementation and the correctness oracle for the fast class below. Its known weakness is that the per-subset reduction is an elementwise multiply-and-sum over a $(U_c \times U_b)$ array, repeated $\binom{D}{k}$ times — no BLAS, poor cache behaviour — which is precisely what section 12 sets out to fix. As measured there, that fix currently pays off only for small $k$, so woodelf_sparse routes the CII metrics through this class by default.

Total cost across the ensemble

Putting the leaf cost back into the loop over the model, with the notation of section 9 ($T$ trees, $L$ leaves per tree, $n$ consumer rows, $m$ background rows), the order-$k$ algorithm costs:

$$O\Bigl(\underbrace{mTL}_{\text{background patterns}} \;+\; \underbrace{n\,T\,L\,\tbinom{D}{k}}_{\text{scatter to consumer rows}} \;+\; \underbrace{\tbinom{D}{k}\,U_c\,U_b\,T\,L}_{\text{core reductions}}\Bigr)$$

Each term generalizes one term of section 9 in a different way, which is worth reading off explicitly:

Where the order enters — and where it does not

Pattern construction is untouched. $mTL$ carries no $k$ at all: routing the background through the trees and uniquifying the patterns happens once, no matter which orders are being computed. The same holds for the consumer routing.

The scatter grows with the number of answers. Section 9's $nTLD$ becomes $nTL\binom{D}{k}$ — one length-$n$ write per subset per leaf rather than one per feature. This term is pure bookkeeping, but at higher orders it stops being negligible.

The core grows with the subset count. $U_c U_b TLD$ becomes $\binom{D}{k} U_c U_b TL$ — one elementwise pass over the pair array per subset. For a range of orders, replace $\binom{D}{k}$ by its sum over $\texttt{orders}(D)$: a range costs extra blocks, not extra passes over the shared pair-level arrays.

Setting $k = 1$ collapses all three back to $O(mTL + nTLD + U_c U_b TLD)$ — exactly the row for MNBackgroundPathToSVectors in section 9.

$O\bigl(\tbinom{F}{k} \cdot 2^{F} \cdot n\bigr)$ model evaluations — exponential in the feature count $F$
MNBackgroundCIIPathToSVectors

Memory is the real ceiling, not time

The returned dictionary holds one length-$n$ array per subset that co-occurs anywhere in the model — up to $\binom{F}{k}$ of them over $F$ features, independent of $T$, $L$ and $D$. At $k = 2$ this is the familiar quadratic interaction matrix; at $k \ge 3$ it grows faster than any term in the runtime above. Where the algorithm scales fine but the output does not, global_importance-style aggregation or a narrower order range is the answer.

A note on the any-order default

With max_order=None a depth-$D$ leaf reports every non-empty subset of its path features: $\sum_{k \ge 1} \binom{D}{k} = 2^D - 1$ output rows, and the same count of elementwise passes. Since the returned dictionary holds one array of length $n$ per subset, on deep trees the output itself — not the algorithm — becomes the binding constraint. Pick an explicit max_order when $D$ is large.

What this unlocks

Background-mode interaction values are now available in the sparse/deep regime for the first time, at any order, with the neighbor leaf trick of section 8 fully intact — an advantage over the path-dependent Linear TreeSHAP route, where the trick has to be switched off for interaction values.

12 · The Fast Approach — MNBackgroundCIIFasterPathToSVectors WIP

Work in progress — not the default

This class is not what woodelf_sparse uses for the CII metrics; section 11's class is. The restructuring below is correct — it is verified against the simple class — but as the measurements later in this section show, it is only faster for small $k$ and becomes dramatically slower beyond the crossover, because the factorization it relies on carries an extra $2^k$ in its row count. The fix is known and sketched at the end of this section; until it lands, this class stays opt-in.

The fast class earns its speed the same way section 6 did — by finding a factorization that separates the consumer index from the background index, so the sum over $b$ becomes a matrix multiplication. The order-$k$ identity is the direct generalization of $\text{pos_bits} = c_d(1 - b_d)$.

The separation identity

Fix a subset $S$ and a candidate split $A \subseteq S$ (the members of $S$ we suppose are the positive literals). By the table of section 2, $d \in A$ requires $c_d = 1, b_d = 0$ and $d \in S \setminus A$ requires $c_d = 0, b_d = 1$. Writing that out and grouping:

$$\prod_{d \in A} c_d(1-b_d) \prod_{d \in S \setminus A} (1-c_d)b_d \;=\; \underbrace{\Bigl[\,p_c\big|_S = A\,\Bigr]}_{\text{consumer only}} \cdot \underbrace{\Bigl[\,p_b\big|_S = \overline{A}\,\Bigr]}_{\text{background only}}$$

The pair contributes to $S$ under split $A$ iff the consumer pattern restricted to $S$ equals $A$, and the background pattern restricted to $S$ equals its complement within $S$. The two factors share no index — which is exactly the property a matmul needs.

At $k = 1$ the two splits $A = \{d\}$ and $A = \emptyset$ give back $c_d \cdot (1 - b_d)$ and $(1 - c_d) \cdot b_d$: sections 6 and 7 are this identity's $k=1$ case.

From identity to matmul

Group the work by split size $a = |A|$. Every pair-level scalar for that size is one array, and every $(S, A)$ pair with $|A| = a$ is one row of a mask matrix:

$$W_a[c, b] = V_a\bigl[p_{c,b}\bigr]\bigl[n_{c,b}\bigr] \cdot \hat{b}_b \cdot \text{valid}_{c,b} \qquad (U_c \times U_b)$$ $$B_a[(S,A),\, b] = \Bigl[\,p_b\big|_S = \overline{A}\,\Bigr] \qquad \Bigl(\tbinom{D}{k}\tbinom{k}{a} \times U_b\Bigr)$$

The background reduction is then one dense matrix multiplication per split size:

$$\mathbf{BM}_a = B_a \cdot W_a^\top \qquad \Bigl(\tbinom{D}{k}\tbinom{k}{a} \times U_c\Bigr)$$

and the consumer side recombines them with its own masks $C_a[(S,A), c] = \bigl[p_c|_S = A\bigr]$:

$$\boxed{\;s[S, c] \;=\; w_\ell \sum_{a=0}^{k} \ \sum_{\substack{A \subseteq S \\ |A| = a}} C_a[(S,A),\, c] \cdot \mathbf{BM}_a[(S,A),\, c]\;}$$
That sum is really a selection

For a given subset $S$ and consumer pattern $c$, the mask $C_a[(S,A), c]$ is $1$ for exactly one split — namely $A = \{d \in S : c_d = 1\}$, which the consumer pattern determines outright — and $0$ for all $2^k - 1$ others. So the double sum picks a single $\mathbf{BM}$ entry per $(S, c)$; writing it as a masked sum simply lets NumPy do the picking without a gather.

Operations in code

c_bits = bits_matrix(consumer_batch, D)          # (D, U_c)
b_bits = bits_matrix(unique_b, D)                 # (D, U_b)

for k, block_start, n_subsets in self._order_row_blocks(D):   # each reported order fills its own rows
    for a in range(k + 1):                                    # one split size at a time
        W = contribution_tables[k][a][p, n] * base              # (U_c, U_b)
        positions, in_A = self._split_index_arrays(D, k, a)

        # background mask is inverted vs A, consumer mask follows A
        b_mask = self._restriction_masks(b_bits, positions, ~in_A)
        BM     = b_mask.astype(np.float64) @ W.T               # (rows, U_b) @ (U_b, U_c) → (rows, U_c)
        c_mask = self._restriction_masks(c_bits, positions, in_A)

        s[block_start:block_start + n_subsets] += (
            (c_mask * BM).reshape(-1, splits_per_subset, batch).sum(axis=1)
        )

Each reported order is an independent instance of the scheme, so the orders simply run one after another, each filling its own block of $s$ rows. The expensive per-pair quantities ($p$, $n$, valid, the frequencies) are built once and shared by all of them.

Keeping memory in check

Three independent bounds

1 · Consumer batching — inherited from section 5.5, bounding $U_c \times U_b$.

2 · Streaming over $a$ — only one $W_a$ exists at a time. The shared $p$, $n$ and valid arrays are computed once, so peak pair-level memory stays at roughly the order-1 level rather than $(k{+}1)\times$ it.

3 · Chunking over subsets — the mask matrices grow as $\binom{D}{k}$, so rows are processed in whole-subset groups bounded by MASK_BATCH, each chunk writing its slice of the preallocated output. This is what keeps $D = 20, k = 3$ (9,120 rows) from materializing a single enormous mask.

Following the analysis of point 3 in the design discussion, all arithmetic stays in float64: the CPU-only gain from float32 (~2×) was not judged worth making $10^{-4}$-level deviations the silent default in a library whose selling point is exactness. The masks are exact in either precision, so the option remains open — most relevantly for a future GPU port, where fp64 throughput is a small fraction of fp32.

Reading the table

The win is real but narrow. Up to $k = 4$ the matmul form is the faster one, peaking at $4.5\times$ around $k = 2$ — the pairwise case, which is also the one most people actually ask for.

Past the crossover it inverts hard. At $k = 7$ the "fast" class is seven times slower than the class it was written to replace. This is not a constant-factor wobble; it is the $2^k$ in the row count overtaking what dgemm buys back.

$k \ge 8$ could not be measured at all. The cached split-index arrays alone project to roughly 4.9 / 17 / 49 GB at $k = 8, 9, 10$ — the same $2^k$ blowup, surfacing as memory rather than time. The simple class has no such cache and ran fine at every order.

Over full 100-tree IEEE-CIS ensembles the shape is the same, just milder: the fast class ran $2\times$–$2.6\times$ ahead at $k = 2$ and $k = 3$ on depth-16 and depth-22 models, dropped to $\approx 1.4\times$ at $k = 4$, and came out behind the simple class at $k = 4$ on a depth-6 model ($0.78\times$–$0.85\times$). That last case is the same effect from the other direction — what matters is $k$ relative to $D$, so a small tree reaches the crossover at a much lower order.

Complexity — what the restructuring changes

Only the core term differs from section 11; the pattern construction and the scatter are shared verbatim. The trade is $\binom{D}{k}$ elementwise passes over a $(U_c \times U_b)$ array, replaced by $\binom{D}{k}2^{k}$ rows of BLAS work:

MNBackgroundCIIPathToSVectors
$O\bigl(mTL + nTL\tbinom{D}{k} + \tbinom{D}{k}\,U_c U_b\,TL\bigr)$ — elementwise
MNBackgroundCIIFasterPathToSVectors
$O\bigl(mTL + nTL\tbinom{D}{k} + \tbinom{D}{k}2^{k}\,U_c U_b\,TL\bigr)$ — BLAS, but $2^k$ more of it

At $k = 1$ this is $\binom{D}{1}2^1 = 2D$, the two matmuls of section 6, and the bet pays off exactly as it did there. But the $2^k$ is a real asymptotic cost, not a constant: section 6 won because BLAS beat elementwise at identical operation counts, whereas here BLAS has to win by a factor of $2^k$ just to break even. The table above is where that stops happening — around $k = 5$ at $D = 22$.

The fix — inclusion–exclusion on the background masks

Expanding the $(1 - b_d)$ factors by inclusion–exclusion turns every background mask into a plain AND-monomial shared across splits, shrinking the matmul rows from $\binom{D}{k}2^k$ to $(k{+}1)\sum_{j \le k}\binom{D}{j}$. That swaps an exponential-in-$k$ factor for a polynomial one: at $D = 16$ it is roughly break-even at $k = 1$, $2.3\times$ fewer rows at $k = 4$, and $12.7\times$ fewer at $k = 10$ — and the gap keeps widening. The cost is replacing the select-like masked sum with a signed multi-term recombination.

This is what would move the crossover out far enough for the class to deserve its name at every order. It is currently recorded as a comment in _compute_s_batch and left unimplemented — which is exactly why this section is marked WIP.
